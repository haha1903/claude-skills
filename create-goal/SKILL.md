# Create Goal

在当前工作目录创建目标文档: `_generated/goal-{topic}.md`

**目标**: 用户调用本 skill 时传入的目标描述（位于 `args`；为空则按「停止条件」处理）。

## 停止条件

不启动:
- `args` 为空时，提示用户提供目标描述（例如: `/create-goal 迁移 Kusto 认证到 MI`），不生成文件。

立即停下:
- 预填过程中发现目标描述歧义严重（可解读为两个以上不同目标）时，停下并向用户澄清，不继续写文件。

## 完成标准

- `_generated/goal-{topic}.md` 已创建（`{topic}` 为主题的短横线英文 slug）。
- 以下 section 已预填（预填规则见下方）:
  - 「目标」「日期」「范围与约束」「非目标」
  - 「完成定义」草案（至少 2 条可观察结果条件）
  - 「待解问题」（至少列出最关键的 1-3 个未知项）
  - 「任务清单」初始任务（从完成定义反推的第一批行动）
  - 「背景上下文」中至少列出 1-3 条前提假设（标注 `[推断]` 或 `[待确认]`），使用户可以快速验证或推翻
- **先读后写**: 当目标涉及现有代码、系统或文件时，AI 必须先用工具读取相关文件（至少读取入口文件/主配置），再预填「背景上下文」和「任务清单」。禁止在未读取实际代码的情况下描述系统现状。
- **预填规则**: 禁止凭空编造事实或推测未知约束（截止日期、负责人等一律写「待确认」）。但对于可通过工具验证的事实（版本号、文件是否存在、API 是否可用），应主动查证后填入 `[已验证]`，而非标注 `[待确认]` 后停下。区分: "不确定且可查" → 去查；"不确定且无法查" → 写待确认。禁止用 `...` 作为唯一内容——要么写出具体内容，要么写「待确认: [需要确认什么]」。
- **显式失败**: 若 AI 发现某条完成定义无法确定验证方式，必须在该 CD 旁标注 `[验证方式待定]` 并在「待解问题」中新增对应条目。禁止留空或写模糊条件后继续。
- 当目标涉及代码或系统行为变更时，完成定义中至少有 1 条验证型条件（含具体输入、期望输出、证据产物路径）。若当前信息不足以写出验证型条件，应写「待确认: 验证场景需调研后补充」而非省略。
- 验证型 CD 的证据必须是可事后复核的持久化产物（文件、日志、截图），禁止以终端输出或内存状态作为唯一证据。当证据是文件时，应指定文件需包含的关键结构（如特定 section header 或字段），避免空文件或无关内容误通过。
- 用户已被告知下一步建议: 从「待解问题」开始，列出核心问题后逐个调研。
- Best-effort: 尝试用 `open -a Typora` 打开文件，失败时不阻塞。

## 自检

- 模板中的 section 是否全部保留？简单目标的「差距分析」「方案对比」「风险与缓解」可标 N/A，其余必须保留占位符。
- 文件名 slug 是否准确反映主题？
- 预填字段中是否有「待确认」遗漏（上下文未提供的信息不应被填入具体值）？
- 完成定义是否全部为**可观察结果**（禁止动作型如"完成调研""修复代码""讨论方案"）？
- 验证型 CD 的证据载体是否为持久化产物（而非终端输出）？是否指定了文件应包含的关键结构？
- 背景上下文中的每条事实是否标注了状态标签？
- 任务清单中的每个任务是否关联了对应的完成定义编号？

## 协作规则

在后续对话中与用户协作推进目标时，遵循以下规则:

1. **任务清单驱动** — 每次对话结束前同步任务清单和相关 section（背景上下文、调研发现等），新增任务标注执行方（🤖/👤/🤝）。
2. **闭环标准** — 活跃任务清空且「完成定义」全部勾选时，状态改为 ✅ 已完成。
3. **变更留痕** — 重要变更（任务增删、关键决策、方向调整）记录到变更日志。
4. **中间检查点** — 完成每个 T-级任务后，输出一句话检查点（已完成什么、验证了什么、下一步做什么）。若无法清晰描述当前状态，立即暂停并向用户确认方向。

## 创建后流水线（严格串行，禁止并行）

Goal 文档创建完成后，按以下顺序执行。每一步必须等前一步完全结束后才开始，禁止提前启动或并行:

### 第一步: 评审与修复

- **命令**: `codex exec --ephemeral --skip-git-repo-check "follow review-goal/SKILL.md to review {goal 文件完整路径}"`
- **禁止 fallback**: codex 是唯一的评审执行者，必须等待其完成，不得自行评审或跳过。
- **修复判断**: 合理的问题直接修复原 goal 文件；不合理的问题不修复，在「变更日志」中记录不采纳原因。
- **告知用户**: 汇报修复了哪些、跳过了哪些（附理由），提示 review 文件路径。

### 第二步: 执行任务（必须在第一步完全结束后才开始）

立即执行所有无阻塞的 🤖 AI 任务，无需等待用户确认:

1. 扫描任务清单，找出满足以下条件的任务: 执行方为 🤖 AI、状态为 ⏳ 待办、阻塞于为空（或所有阻塞任务已完成）
2. 按依赖顺序逐个执行（被依赖的先做）
3. 每完成一个任务，**立即回写 goal 文件**:
   - 将该任务从「活跃任务」移入「已完成」表，填写完成时间和完成证据
   - 若该任务的完成使某条 CD 可勾选，将对应 `- [ ] CD-X` 改为 `- [x] CD-X`
   - 在变更日志追加一行记录
4. 若执行中发现新的阻塞（需用户决策、外部依赖不可用），停在当前任务并标注阻塞原因，继续执行其他无阻塞任务
5. 所有可执行任务完成后，再次检查完成定义是否全部满足；若满足则将文档顶部状态改为 `✅ 已完成`
6. 向用户汇报: 完成了哪些任务、产出了哪些文件、是否有剩余阻塞任务

**关键**: 执行产出文件 ≠ 完成。必须同步更新 goal 文件中的任务状态、CD 勾选和文档状态，否则视为未完成。

**原则**: 执行方为 🤖 AI + 无阻塞 = 全自动完成，不询问不等待。只有执行方为 👤 人工或 🤝 协作的任务才暂停等待用户。

## 硬约束

- 所有输出内容必须为简体中文。
- 模板中的 section 全部保留。简单目标（单一明确行动、无需方案选择、无外部依赖）的「差距分析」「方案对比」「风险与缓减」可标注 `N/A — 目标直接可执行，无需此分析`，其余 section 即使暂时为空也保留占位符结构。
