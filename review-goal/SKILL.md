# Goal 文档评审与核验

把一份 goal 文档从"能看"推进到"能高质量完成"。

**目标文件**: 用户调用本 skill 时传入的文件路径（位于 `args`）；若为空则按「停止条件」处理。

## 停止条件

不启动:
- `args` 为空且用户未贴内容时，提示用户提供 goal 文件路径。
- 指定文件路径不存在时，提示正确路径。
- 文件为空或无法读取时，告知用户并停止。
- 文件明显不是 goal/执行类文档（如纯代码文件、配置文件）时，告知用户不适用。

## 只读约束

review 阶段只读取和核验，**不修改 goal 原文**。所有修改建议以文本形式输出到 review 文件中，由 `create-goal` skill 的自动修复流程或用户手动应用。

## 适用范围

适用于以下文档：

- `_generated/goal-*.md` 这类目标文档
- 基于 `create-goal` 模板继续演化出来的执行文档
- PRD、调研计划、重构计划、执行方案，只要核心目的是推动某个目标闭环

如果用户给了文件路径，先读文件再评审。如果用户直接贴内容，直接按内容评审。必要时可参考以下文件作为基线，但不要为了"格式一致"而牺牲执行效率：

- 结构基线：`/Users/haichang/.claude/skills/create-goal/SKILL.md`

## 核心目标

这份评审说明的目标不是挑文案毛病，而是确保这份 goal 文档：

- 真的能完成，而不是停留在"看起来很完整"
- 以更优路径完成，尽量减少返工、错序和低价值工作
- 把关键不确定性、决策门和风险暴露出来
- 文档里的关键事实经得起核验，而不是只在文档里说得通
- 没有漏掉更优方案、更低风险路径或更高杠杆的动作
- 让后续执行者可以直接按文档推进，而不是重新理解一遍

## 核心原则

- 目标服务执行，不服务排版。章节名称允许调整，只要信息完整。
- 必须逐段检验所有关键章节（除非用户明确限定范围），不能只挑大问题就结束。
- 不能把文档描述直接当事实。关键结论必须核验，未核验的写"文档声称"或"待验证"。
- review 不止于指出问题，还要探索更优方案和替代路径。
- 完成定义优先于任务清单。任务只是手段，不是结果。
- 先证据后结论，先关键路径后外围优化。
- review 只读不改 goal 原文。最终输出必须落盘到 `_generated/`。

## 对照基线

优先对照 `/Users/haichang/.claude/skills/create-goal/SKILL.md` 的语义结构，而不是机械要求章节同名。重点检查这些信息是否存在且有效：

- 目标、日期、状态
- 范围与约束
- 非目标
- 完成定义
- 背景上下文
- 待解问题，或已经收敛后的关键结论
- 调研发现与证据
- 差距分析或等价信息
- 方案对比或等价决策过程
- 风险与缓解
- 决策记录
- 任务清单
- 变更日志
- 未知信息是否明确标为"待确认"，而不是被臆测填充

如果某个章节消失了，但对应信息已经在别处被更清楚地表达，不要因为名字不同就判定为问题。只有信息本身缺失、失真、错位或无助于执行时，才算问题。

## 严重级别判定标准

| 级别 | 判定规则 | 后果 |
|------|----------|------|
| 阻断 | 不修则无法开始执行或必然失败 | 必须先修，不可跳过 |
| 高 | 不修会导致返工、错序或关键遗漏 | 强烈建议修复后再执行 |
| 中 | 影响质量或效率但不阻塞推进 | 可在执行中补强 |
| 低 | 局部优化、表达改善、格式问题 | 可选修复 |

## 逐段检验要求

除非用户明确说"只看某一段"或"只看关键路径"，否则必须逐段覆盖以下部份。对每个部份至少给出：

- 结论：`通过` / `基本通过` / `需补强` / `关键问题` / `缺失`
- 一句最主要的问题
- 一句最直接的修改建议

默认按以下顺序检验：

| 部份 | 重点检查 | 判高/阻断条件 |
|------|----------|---------------|
| 标题 / 目标 / 日期 / 状态 | 目标是否单一清晰，阶段是否明确，状态是否和实际进度一致 | 混合多方向、结果写成活动清单 |
| 范围与约束 | 包含 / 不包含 / 约束是否收敛，是否会引发 scope creep | 缺少非目标或约束，执行易无限扩张 |
| 非目标 | 是否明确排除了容易扩张的方向 | — |
| 完成定义 | 是否是结果条件，是否可验证，是否能判断真正闭环 | 存在动作型条件（"完成调研""修复代码""讨论方案"） |
| 背景上下文 | 是否给出基线、规模、关键事实、证据落点 | 关键结论无证据来源，猜测与事实混写，未知项未标"待确认" |
| 待解问题 | 未决事项是否被显式收拢成问题，而不是散落在正文里 | 分歧未收敛、无决策人 |
| 调研发现 | 现状 / 证据 / 影响是否完整，条目之间结构是否一致 | — |
| 差距分析 | 是否说明当前状态、目标状态和差距 | — |
| 方案对比 | 是否真的存在备选方案，比较维度是否支撑结论 | 低价值项占关键路径、缺决策门、遗漏更优替代 |
| 风险与缓解 | 是否写清触发条件、影响面、缓解和必要时的回滚 | 只列名词无触发条件/缓解/回滚 |
| 决策记录 | 已决 / 待决是否清晰，是否有明确决策人 | 分歧未收敛、无决策人 |
| 任务清单 | 是否服务完成定义，是否有执行方、状态、依赖、阻塞关系 | 任务与完成定义无映射、过大无法验证、缺执行方/依赖；无持续维护机制 |
| 变更日志 | 是否能反映关键方向调整和决策变化 | — |

如果文档没有显式出现某个章节，要先判断该语义是否已经被别处覆盖：

- 如果语义已覆盖但表达分散，结论写 `需补强`
- 如果语义完全不存在，结论写 `缺失`
- 不要因为作者改了标题就误判为缺失

## 事实核验要求

逐段检验之后，必须核验文档中影响执行决策的关键事实。**范围约束**: 只核验影响完成定义、关键路径、风险前提、任务依赖的事实，优先核验 Top 5-10 个最关键事实，不追求穷举。优先核验：

- 文件、目录、模块、函数、脚本、接口是否真的存在
- 调用方数量、依赖关系、消费者清单是否属实
- 指标、计数、warning/error 数量、run ID、版本、数据规模是否能追溯到实际 artifact
- 风险前提是否成立，例如"没有并发读者""可以直接回滚""只有 1 个调用方"
- 建议动作的前置条件是否真实存在，例如某模块是否真的无调用方、某功能是否真的可删

对每个重要事实，尽量通过以下方式验证：

- 读实际文件和相关代码
- 用 `rg` 检查调用方、引用点、配置项
- 读取生成产物、日志、validation 报告、任务输出
- 必要时运行安全的只读命令获取现状
- 如果事实涉及外部系统或时效性信息，使用权威来源核验

事实核验结论必须明确标注为以下之一：

- `已验证`：有直接证据支持
- `部分验证`：验证了其中一部分，但还有未闭合的假设
- `未验证`：文档中提出了说法，但当前没有拿到证据
- `与事实不符`：核验结果和文档描述冲突

如果无法核验，必须明确说明缺了什么证据，不能把文档原话当结论复述。

## 方案探索要求

当文档只给出一个方案且现实中明显存在替代路径时，指出"方案对比不完整"并补出最值得比较的备选（如更小改动的路径、keep/simplify/postpone/do-nothing 基线）。**约束:** 替代方案必须服务当前完成定义，不能扩大目标范围，不能把 review 变成新 PRD。

## 跨段一致性检查

逐段检验和事实核验之后，必须再检查这些跨段关系是否一致：

- 目标 vs 范围与非目标：目标是否和边界一致
- 目标 vs 完成定义：完成定义是否真的在验证目标达成
- 完成定义 vs 任务清单：任务是否映射到完成定义，而不是各做各的
- 待解问题 / 决策记录 vs 活跃任务：未决事项是否已经变成明确的决策门或阻塞关系
- 风险与缓解 vs 执行矩阵：高风险项是否被排在了不合理的位置
- 状态 / 变更日志 vs 文档内容：文档是否还处于调研阶段，还是实际上已经进入执行阶段
- 文档事实 vs 任务安排：任务是否建立在已验证事实之上，而不是建立在未经验证的假设上

**路径优化动作标签**（用于路径优化建议）:

- `前置`：必须先解决，否则后面大概率返工
- `删除`：低价值、重复、不服务当前完成定义
- `合并`：本质是一件事，不应拆成独立任务
- `延后`：值得做，但不应进入当前主路径
- `并行`：互不阻塞，可同时推进
- `保留`：当前顺序合理

## 工作流

按「核心目标」6 条标准自主迭代，确保输出符合「默认输出格式」。每个问题必须写清: 现状哪里弱、为什么影响完成质量、应如何具体修改（给可直接替换的文本，而非"建议补充细节"）。默认用中文回复。

最终输出必须落盘到 `_generated/`:
- 用户给了 goal 文件路径 → `_generated/review-{goal 文件名去掉扩展名}.md`
- 用户直接贴内容 → `_generated/review-goal-output-{YYYY-MM-DD-HHMMSS}.md`
- 最终回复里附上已保存文件路径

## 输出落盘规则

- 最终输出必须完整落盘，不能只保存摘要。
- **路径规则**: 输出到输入 goal 文件所在目录的 `_generated/` 子目录（如输入本身在 `_generated/` 下则同级）。与 `create-goal` skill 保持一致。
- 如果目标文件是 `_generated/goal-foo.md`，输出文件为 `_generated/review-goal-foo.md`。
- 如果目标文件是 `/path/to/goal-bar.md`，输出文件为 `/path/to/_generated/review-goal-bar.md`。
- 如果同名文件已存在，直接覆盖为最新版本即可。
- 对话中的最终回复要明确写出保存路径。
